# 渠道关单与全额退款

控制端0.10 / 数据库迁移v10。支付宝和微信支持渠道关单、原付款全额退款、审批与持久化结果核实。常见易支付没有可信的资金操作响应协议，本轮不提供易支付关单或退款。所有验证使用本机临时密钥、TLS网关和独立数据库，没有操作真实商户资金。

## 启用与权限

`PAYMENT_ACTIONS_ENABLED` 默认为空或 `false`；仅显式 `true` 启用资金消费者、退款审批和渠道关单。其他值使控制端启动失败。开关关闭时仍可记录和查看退款申请，审批/关单API返回503；已有任务留在数据库，重启并开启后继续处理。关闭开关并重启会取消本进程，无法撤回渠道已经受理的请求。

先按 [支付接入](payments.md) 配置支付宝或微信商户、验签密钥和产品权限，完成目标商户沙箱或小额验收，再在部署环境设置开关并重启控制端。不要把商户密钥、账号密码或支付链接提交到Git。公共配置仅返回开关布尔值。

| 操作 | 管理员 | 财务 | 客服、运维、普通用户 |
| --- | --- | --- | --- |
| 查看退款记录 | 可以 | 可以 | 拒绝 |
| 提交全额退款申请 | 可以 | 可以 | 拒绝 |
| 审批或重新核实退款 | 当前密码验证 | 拒绝 | 拒绝 |
| 提交或重新核实渠道关单 | 当前密码验证 | 当前密码验证 | 拒绝 |

资金写操作同时按直接对端IP、当前用户、操作用途限流，各5次/分钟。写请求要求Origin和JSON；生产环境还要求邮箱验证。审批/关单校验当前密码，并在数据库事务中锁定角色和相同的 `security_version`，防止校验后并发降权或改密仍可提交。密码不写入队列、审计或浏览器存储。

## 退款流程

1. 在“支付流水”选择支付宝或微信的已付款订单，填写原因，申请原付款全额退款。原因去除首尾空格后必须为1–256个UTF-8字节，拒绝控制字符。只能使用订单快照金额、CNY、原交易号；请求不接受自填金额。
2. “退款管理”展示申请。一个支付记录只建立一个退款编号，重复申请返回原申请，不修改原因或交易数据。申请不调用支付机构，也不撤销权益。
3. 管理员核对订单、金额和原因，输入当前密码审批。系统持久化审批人和待处理任务后返回202。审批重复提交不会产生第二笔退款。
4. 消费者先查询同一退款编号。只有验签通过且明确表示该退款不存在，才提交退款。超时、坏签名、业务错误、原交易不存在均不作为可提交的退款缺失证明。每次重试使用同一编号；收到成功响应也要精确核对原支付、原交易、退款编号、金额和币种。支付宝提交响应不能单独绑定退款编号，因此还会查询准确的 `out_request_no`。
5. 只有渠道明确成功，才在一个数据库事务中记录退款成功、原订单改为 `refunded`、撤销该订单的权益周期、写入 `entitlement.revoked` 事务事件和审计。任一步失败全部回滚；下一次仍查询原退款编号恢复结果。

原 `payment_intents` 保留 `paid` 和原交易号，`payment_events` 保留原收款凭证。退款后原支付通知再次到达仍幂等，不重新开通权益。后续续费周期及其日期保持原状，不重排已购买的其他订单。权益撤销事件沿用既有节点消费者；事件已投递与节点实际应用仍须分别查看。已过期或已人工撤销的原权益也可以记录真实退款，不会恢复该权益。

本轮仅支持原付款全额退款，不包含部分退款、按剩余天数折算、余额支付、跨订单合并退款或额外赔付。退款失败不自动重建新编号；渠道 `failed` 状态需人工核查。微信 `ABNORMAL` 等结果进入 `manual_required`。

## 渠道关单

已有支付意图不能用普通用户的本地关闭接口取消。在后台“支付流水”由管理员或财务填写原因并验证当前密码后，原订单进入 `closing`，停止新收银台请求，读取和并发保存也不再返回付款链接。已经打开的渠道页面仍需要支付机构真实关单，页面状态无法代替渠道确认。

消费者先可信查询原支付：已付款则履约并保留收款事实；未付款或明确尚未建立交易，才提交关单。只有签名验证通过的支付宝关单成功、微信204关单响应，或精确绑定原订单的可信查询明确确认交易已关闭，才能改为 `closed`。后者用于恢复渠道已关单但成功响应丢失的情况。`NOT_FOUND` 仅表示查无交易，不能表示已关闭；支付宝PagePay链接可能要在浏览器打开后才建立远端交易，因此此时保持 `closing`、继续核实并最终转人工。

付款通知可能与关单交错。对于已固定的支付意图，合法迟到付款仍然履约，清除 `closed_at`，订单恢复为 `paid`。没有支付意图的本地已关闭订单仍不能支付或通过开发结算开通。已经退款的订单不会被旧支付通知重新开通。

## 任务恢复和状态

任务提交数据库后才做网络请求，不跨网络持有行锁。每次领取具有60秒租约和随机令牌；单次操作总时限26秒，完成事务另限5秒。旧租约不能提交本地完成结果。提交前持久化 `submitted` 标识，即使渠道受理后网络断开，仍可用原编号查回。

正常处理中不消耗错误预算；等待按检查次数从30秒退避到最多1800秒。错误按连续失败次数退避，8次连续错误或7天核实期限后进入 `manual_required`，保留未知财务状态，不伪造成功或失败。该轮任务停止自动外呼；管理员可在退款管理验证当前密码后“重新核实退款”，管理员/财务可在支付流水验证当前密码后“重新核实关单”，沿用原编号、重置检查次数并开启新的7天期限。正在处理或已完成的重复提交幂等。

退款状态依次为 `requested` → `queued` → `processing` → `succeeded`，异常可能进入 `failed` 或 `manual_required`。API成功排队不等于退款成功。支付流水的关单中订单展示关单任务的最近结果、失败次数和下一次检查时间；完成关单不再显示付款查询时间。处理记录只追加有限来源/结果枚举，不保存渠道原文、验签头、密码或商户配置。财务记录和退款列表均为最近100条。

## API

| 接口 | 请求 | 权限与结果 |
| --- | --- | --- |
| `POST /api/v1/admin/payments/{id}/refund` | `{reason}` | `refunds.request`；200，返回不可变申请 |
| `GET /api/v1/admin/refunds` | 无筛选参数 | `refunds.read`；200，`{items}` |
| `POST /api/v1/admin/refunds/{id}/approve` | `{current_password}` | `refunds.approve`；开关启用，202 |
| `POST /api/v1/admin/payments/{id}/close` | `{reason,current_password}` | `payments.close`；开关启用，202 |

完整字段及错误见 [OpenAPI](../api/openapi.json)。未登录401；权限变化403；不存在404；状态或渠道不支持409；限流429；开关未启用503。未知请求字段和退款列表筛选参数拒绝，不接受手工修改账务事实。

## 验收边界

本轮覆盖真实RSA签名的本地网关协议、超时与验签失败、稳定编号恢复、租约回收、事务失败回滚、关单/付款交错、退款后通知重放、权限与密码，以及后台操作流程。没有配置真实商户、没有向外部收款人或付款人发起支付/退款，也不代表官方沙箱、商户产品权限或资金到账时效已验收。生产启用仍需依据目标商户当前接口文档核对、测试权限和可退款期限，并用渠道商户账单验证结果。v11已实现规范CSV账单导入和差异复核，见 [商户账单](merchant-statements.md)；v12增加受限原始格式和默认关闭的按需官方下载，见 [原始账单](native-bills.md)；v13增加默认停用的[每日下载计划](bill-schedules.md)；v14增加[来源级费用与渠道金额预期比较](statement-financials.md)，仍不影响资金操作；更多格式、真实商户、资金流水及完整结算验收仍待完成。
