# 支付异常处理与运营

控制端0.9 / 数据库迁移v9 增加持久化逐笔付款核实、订单时限和后台支付流水。没有连接真实商户，也没有执行真实扣款、关单或退款。商户配置与三个渠道的验签边界见 [支付接入](payments.md)。

## 订单与支付状态

订单包含 `expires_at` 和可空的 `closed_at`。新订单在创建30分钟后到期；迁移中的已有订单按原 `created_at + 30分钟` 回填到期时间，不重新延长付款窗口。

| 订单状态 | 含义与可执行操作 |
| --- | --- |
| `pending` | 尚未确认付款且未过期；可以选择支付方式。只有尚未建立支付意图的订单可以本地关闭 |
| `expired` | 已超过本地付款窗口；不能创建新收银台，仍可接收有效付款通知及可信查询确认 |
| `closed` | 用户已关闭未建立支付意图的订单，记录 `closed_at`；不再接受新付款操作 |
| `paid` | 付款证据与权益已原子提交 |

调度器定量将到期 `pending` 订单改为 `expired`。即使调度尚未运行，支付创建也检查真实到期时间，不通过调度延迟延长付款窗口。支付意图本身保留 `pending` / `ready` / `paid`，不会把本地订单过期冒充为支付机构拒绝或关闭了交易。

关闭请求要求本人会话、JSON和可信Origin。已存在任何支付意图时返回409，即使尚未收到收银台结果或订单已经过期；本轮不调用支付机构关闭接口，不能承诺旧二维码或旧跳转链接失效。用户新建订单时应先核实旧订单是否已经付款，多个订单分别付款会分别产生购买权益。

合法迟到通知或核实结果可以将 `expired` 订单履约为 `paid`，仍使用原购买快照。此路径与正常付款相同，交易号去重、金额/币种检查及权益/事件原子提交均保持有效；关闭未发起支付的订单不接受此路径。

## 自动补单

正常启动控制端会运行支付调度与核实消费者。订单到期扫描不依赖启用真实支付渠道；只有已存在且对应渠道已配置的支付宝/微信意图才会调用商户查询接口，不会创建新的收款单或发起扣款。

核实任务持久化到 PostgreSQL，首查安排在支付意图创建30秒后，领取租约为30秒。任务使用租约和独立领取令牌，多控制端通过 `SKIP LOCKED` 分工，网络查询期间不持有数据库行锁。进程中断后租约可回收；旧领取者不能覆盖新领取者的调度结果。消费者只接受适配器验签且与当前支付ID、金额和币种相符的结果，后续仍调用既有原子履约过程。

| 任务状态 | 含义 |
| --- | --- |
| `queued` | 已安排核实 |
| `processing` | 某消费者租约内正在核实 |
| `waiting` | 已记录结果，等待下次检查 |
| `paid` | 本地已确认付款 |
| `manual_required` | 已超过自动处理边界，需要人员处理 |
| `waiting_callback` | 后台摘要对易支付显示的状态，等待有效签名通知；不是自动查询任务 |

未付款是有效业务结果，不计为查询失败。网络、验签、数据冲突或渠道不可用只记录有限错误类别，执行30秒起、最长30分钟的指数退避重试；连续8次失败进入 `manual_required`。自动观察窗口为7天，超过窗口也进入人工处理，而不会将订单冒充为网关已关闭。人工重新排队后开始新的7天窗口；已经确认的付款与已关闭订单不能通过该操作改写。

易支付旧版查询没有可信响应签名，因此不生成自动查询任务，也不能通过后台重新排队把无签名结果变成付款事实。有效签名通知仍会正常履约。发现通知缺失时应联系服务商检查投递；后台没有手工填写“已付款”的入口。

## 后台支付流水

管理员和财务分别通过 `payments.read`、`payments.retry` 权限查看流水及重新排队。客服、运维和普通用户不能访问支付运营接口；生产环境还要求邮箱已验证。

后台显示最近100笔支付记录，支持支付状态、渠道和完整订单ID的精确筛选；`status=manual_required` 选择需要人工处理的核实任务。摘要包括订单、账号邮箱、快照金额、渠道交易号、订单/支付状态，以及核实任务的状态、失败次数、最近结果和下次检查时间。摘要不包含收银台URL、签名、密钥、通知正文或验签头。

处理记录只追加有限来源和结果：收银台创建、通知、用户查询、自动查询、关闭与重新排队。未通过验签的通知不会从未验证正文提取订单身份并伪造归属；可以记录不绑定支付ID的通用拒绝结果，并通过“最近处理记录”查看。无效通知按渠道和直接对端IP每分钟最多保留10条样本；超限仍拒绝请求，但不继续追加记录，合法签名通知不受该采样限制。记录有数据库不可变约束，不能通过普通后台修改或删除；这不等于具备数据库管理员级别的防篡改能力。

| 方法与路径 | 行为 |
| --- | --- |
| `GET /api/v1/admin/payments` | `{items:[...]}`，支持 `status`、`provider`、`order_id` 精确筛选，最多100条 |
| `GET /api/v1/admin/payment-activity` | 全局最近100条处理记录，包含无法绑定订单的验签拒绝分类 |
| `GET /api/v1/admin/payments/{id}/activity` | 返回指定支付意图最近处理记录；`id` 是支付ID，不是订单ID |
| `POST /api/v1/admin/payments/{id}/retry` | 提交 `{}` 重新安排支付宝/微信核实；有审计，不直接更改付款或权益 |
| `POST /api/v1/orders/{id}/close` | 当前用户提交 `{}` 关闭没有支付意图的本人订单 |

人工重新排队也要求可信Origin和JSON。处理中的有效租约、已付款、易支付或其他不允许的状态会拒绝；具体错误以API响应为准。单次渠道查询成功仅表示该笔支付被核实，不是商户账单对账或实收资金结算证明。

## 边界与验收

v10已增加默认关闭的支付宝/微信网关关单和全额退款审批，见 [资金操作](payment-actions.md)。v11已增加规范CSV账单导入和差异复核，见 [商户账单](merchant-statements.md)。v12增加受限原始格式与默认关闭的按需官方下载，见 [原始账单](native-bills.md)。v13增加默认停用的[每日下载计划](bill-schedules.md)。真实商户/官方沙箱、更多格式及余额对账仍待完成。没有可用商户配置时不发起外部查询；已有任务会记录“渠道未启用”并退避，达到边界后转人工处理，不会改为假成功。配置真实商户后后台核实会向该渠道发出查询请求，需安排查询配额、渠道权限和平台验签密钥轮换。

本机数据库、协议与浏览器检查的执行结果由 [verification.md](verification.md) 记录。模拟渠道和临时密钥测试不能替代真实商户联调，也不能证明通知最终到达率或公网性能。
